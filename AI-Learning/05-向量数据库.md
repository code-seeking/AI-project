# 第 05 课：向量数据库

> **核心问题**：怎么在百万数据中快速找到"语义相似"的内容？
> **预计时间**：2 天
> **前置知识**：第 04 课（Embedding 与语义空间）

## 一、为什么需要向量数据库？

你已经会计算两个向量的相似度了。但问题来了：

```
你有 100 万份简历 → 每份简历一个向量（1536 维）
用户提问 → 得到问题向量
朴素做法：遍历 100 万个向量，逐一算余弦相似度
问题：100 万 × 1536 维 = 每秒只能查几次，太慢！
```

**向量数据库的使命**：在**毫秒级**内，从百万/亿级向量中找到最相似的 Top-K 个。

---

## 二、核心原理：近似最近邻搜索（ANN）

### 2.1 精确搜索 vs 近似搜索

```
精确最近邻（KNN）：遍历全部向量，100% 准确，但慢
近似最近邻（ANN）：牺牲一点点准确率，换来百倍速度 ⭐
```

### 2.2 三大 ANN 算法

#### 算法 1：HNSW（Hierarchical Navigable Small World）—— 最流行

**直观类比**：想象找一家餐厅，你不会从家门口一家一家走（精确搜索），而是：
1. 先看"城市"级别的地图 → 定位到区
2. 再看"区"级别 → 定位到街道
3. 最后看"街道"级别 → 找到餐厅

**HNSW 就是分层图**：
```
第 3 层（粗粒度）：少量节点，快速定位区域
第 2 层（中粒度）：更多节点，缩小范围
第 1 层（细粒度）：全部节点，精确找邻居

查询时从顶层开始，逐层下降，每层只走几步
```

**特点**：速度快（毫秒级）、召回率高、内存占用较大

#### 算法 2：IVF（Inverted File Index）—— 倒排索引

**直观类比**：图书馆找书。你不是一本一本翻，而是：
1. 先看分类（计算机类）
2. 再看书架（Java 开发）
3. 最后在书架上找

**IVF 实现**：
```
第一步（聚类）：把 100 万向量用 K-Means 聚成 1000 个簇
第二步（查询）：
  1. 算出查询向量最近的几个簇（比如 10 个）
  2. 只在 10 个簇内精确搜索（1000 个向量）
  3. 复杂度从 100 万 → 1 万，快 100 倍

搜索的簇越多 → 越准越慢
```

#### 算法 3：PQ（Product Quantization）—— 压缩

**核心思想**：把 1536 维向量压缩成很小的编码，减少内存和计算量。

```
把 1536 维分成 96 组，每组 16 维
每组用一个码本（codebook）表示，比如 256 个码字
最终每个向量 = 96 个码字索引 = 96 个字节！

代价：有损压缩，召回率略降
```

### 2.3 实战组合

```
工业界常用组合：
IVF + PQ  → 内存小、速度快、精度尚可（适合亿级数据）
HNSW      → 最快、召回最好、但吃内存（适合百万级）
HNSW + PQ → 平衡方案（pgvector 等支持）
```

**你的场景（几十万简历/文档）→ HNSW 就够了**

## 三、主流向量数据库对比

| 数据库 | 特点 | 适用场景 |
|--------|------|---------|
| **pgvector**（PostgreSQL 扩展）| 复用现有 PG，SQL 生态 | 中小规模（百万级），已有 PG 的项目 ✅ |
| **Milvus** | 专用向量库，功能全 | 大规模（亿级），专业检索 |
| **Qdrant** | Rust 实现，性能好 | 大规模，独立部署 |
| **Chroma** | 轻量，Python 友好 | 原型/PoC，小项目 |
| **Weaviate** | 带 Schema，多模态 | 需要复杂过滤 |
| **Redis（vector）** | 内存级速度 | 缓存/实时场景 |

**为什么你的项目用 pgvector？**
- 已经在用 PostgreSQL，零额外基础设施
- 简历/文档和向量放一起，事务、备份、权限都统一
- 百万级数据 HNSW 完全够用

## 四、pgvector 实战（你项目的核心）

### 4.1 安装与启用

```sql
-- 1. 启用扩展
CREATE EXTENSION IF NOT EXISTS vector;

-- 2. 建表（带向量列）
CREATE TABLE resume_embedding (
    id BIGSERIAL PRIMARY KEY,
    resume_id BIGINT NOT NULL,
    chunk_text TEXT NOT NULL,           -- 原始文本片段
    chunk_index INT NOT NULL,           -- 片段序号
    embedding vector(1536) NOT NULL,    -- 向量列（维度必须匹配）
    created_at TIMESTAMP DEFAULT NOW()
);

-- 3. 创建 HNSW 索引（加速检索）
CREATE INDEX idx_resume_embedding_hnsw
ON resume_embedding
USING hnsw (embedding vector_cosine_ops);

-- 常用索引类型：
-- vector_cosine_ops   → 余弦相似度
-- vector_l2_ops       → 欧氏距离
-- vector_ip_ops       → 内积
```

### 4.2 插入向量

```sql
INSERT INTO resume_embedding (resume_id, chunk_text, chunk_index, embedding)
VALUES (1, '张三，5年Java经验', 0, '[0.1,0.2,0.3,...]');
```

### 4.3 相似度检索

```sql
-- 找出与目标向量最相似的 5 条
SELECT resume_id, chunk_text,
       1 - (embedding <=> '[0.12,0.34,...]') AS similarity
FROM resume_embedding
ORDER BY embedding <=> '[0.12,0.34,...]'
LIMIT 5;

-- pgvector 运算符：
-- <=>  余弦距离（越小越相似）
-- <->  欧氏距离
-- <#>  内积（负值，越大越相似）
```

### 4.4 混合过滤

```sql
-- 带条件的检索（比如只查某个候选人的简历）
SELECT chunk_text,
       1 - (embedding <=> '[0.12,...]') AS similarity
FROM resume_embedding
WHERE resume_id = 100
ORDER BY embedding <=> '[0.12,...]'
LIMIT 5;
```

## 五点六、Java 开发者视角：pgvector 完整实战

```java
/**
 * Java + Spring Boot + pgvector 完整示例
 */
@Service
public class VectorDatabaseService {

    @Autowired
    private JdbcTemplate jdbcTemplate;

    @Autowired
    private EmbeddingModel embeddingModel;

    /**
     * 1. 初始化向量表和索引
     */
    @PostConstruct
    public void initVectorTable() {
        // 启用pgvector扩展
        jdbcTemplate.execute("CREATE EXTENSION IF NOT EXISTS vector");
        
        // 创建表
        jdbcTemplate.execute("""
            CREATE TABLE IF NOT EXISTS resume_embedding (
                id BIGSERIAL PRIMARY KEY,
                resume_id BIGINT NOT NULL,
                chunk_text TEXT NOT NULL,
                chunk_index INT NOT NULL,
                embedding vector(1024) NOT NULL,
                created_at TIMESTAMP DEFAULT NOW()
            )
        """);
        
        // 创建HNSW索引
        jdbcTemplate.execute("""
            CREATE INDEX IF NOT EXISTS idx_resume_embedding_hnsw
            ON resume_embedding
            USING hnsw (embedding vector_cosine_ops)
            WITH (m = 16, ef_construction = 64)
        """);
    }

    /**
     * 2. 插入向量（批量）
     */
    public void batchInsertEmbeddings(Long resumeId, List<String> chunks) {
        // 批量Embedding
        List<float[]> vectors = chunks.stream()
            .map(chunk -> embeddingModel.call(chunk))
            .collect(Collectors.toList());
        
        // 批量插入
        String sql = """
            INSERT INTO resume_embedding (resume_id, chunk_text, chunk_index, embedding)
            VALUES (?, ?, ?, ?::vector)
        """;
        
        for (int i = 0; i < chunks.size(); i++) {
            jdbcTemplate.update(sql, 
                resumeId, 
                chunks.get(i), 
                i,
                arrayToVectorString(vectors.get(i))
            );
        }
    }

    /**
     * 3. 相似度检索（Top-K）
     */
    public List<SearchResult> searchTopK(String query, int topK, double threshold) {
        // 查询向量化
        float[] queryVector = embeddingModel.call(query);
        String vectorStr = arrayToVectorString(queryVector);
        
        // SQL检索
        String sql = """
            SELECT resume_id, chunk_text,
                   1 - (embedding <=> ?::vector) AS similarity
            FROM resume_embedding
            WHERE 1 - (embedding <=> ?::vector) > ?
            ORDER BY embedding <=> ?::vector
            LIMIT ?
        """;
        
        return jdbcTemplate.query(sql, 
            (rs, rowNum) -> new SearchResult(
                rs.getLong("resume_id"),
                rs.getString("chunk_text"),
                rs.getDouble("similarity")
            ),
            vectorStr, vectorStr, threshold, vectorStr, topK
        );
    }

    /**
     * 4. 混合查询（向量 + 元数据过滤）
     */
    public List<SearchResult> searchWithFilter(
            String query, 
            Long candidateId,
            int topK) {
        
        float[] queryVector = embeddingModel.call(query);
        String vectorStr = arrayToVectorString(queryVector);
        
        String sql = """
            SELECT resume_id, chunk_text,
                   1 - (embedding <=> ?::vector) AS similarity
            FROM resume_embedding
            WHERE resume_id = ?
              AND 1 - (embedding <=> ?::vector) > 0.6
            ORDER BY embedding <=> ?::vector
            LIMIT ?
        """;
        
        return jdbcTemplate.query(sql,
            (rs, rowNum) -> new SearchResult(
                rs.getLong("resume_id"),
                rs.getString("chunk_text"),
                rs.getDouble("similarity")
            ),
            vectorStr, candidateId, vectorStr, vectorStr, topK
        );
    }

    /**
     * 5. float[] 转 pgvector 格式
     */
    private String arrayToVectorString(float[] vector) {
        StringBuilder sb = new StringBuilder("[");
        for (int i = 0; i < vector.length; i++) {
            if (i > 0) sb.append(",");
            sb.append(vector[i]);
        }
        sb.append("]");
        return sb.toString();
    }
}
```

> 💡 **生产建议**：
> - 批量插入时用事务包裹，保证原子性
> - 查询时设置合理的超时（如5秒）
> - 定期 VACUUM ANALYZE 保持性能

## 六、关键设计：向量 + 元数据

**纯向量检索不够**，必须结合元数据过滤：

```
场景：知识库问答
用户问："Spring Boot 怎么配置数据源？"
你需要：
1. 向量检索：找到内容相关的 chunk
2. 元数据过滤：只检索指定知识库/指定权限范围
3. 结果：Top-K chunk 文本 → 送给 LLM

设计 schema 时加这些元数据字段：
- document_id     → 属于哪篇文档
- knowledge_base_id → 属于哪个知识库（权限隔离）
- chunk_index     → 块顺序（还原上下文用）
- title/type      → 业务属性
- created_at      → 时效性过滤
```

## 六、向量数据库运维要点

### 6.1 索引选择

```
数据量 < 10 万  → 甚至不用索引，暴力扫描也行
数据量 < 100 万 → HNSW（m=16, ef_construction=64）
数据量 > 1000 万 → IVF+PQ 或换专用库

HNSW 参数：
- m（每层最大连接数）：越大越准越慢，默认 16
- ef_construction（构建时探索）：越大索引质量越高，默认 64
- ef_search（查询时探索）：查询时动态调，越大越准越慢
```

### 6.2 常见坑

```
坑 1：维度不一致
  插入的向量维度 ≠ 建表声明的维度 → 报错
  换 Embedding 模型时必须重建表/加列

坑 2：忘建索引
  数据量大了才发现没建索引 → 查询秒级变毫秒级的差距

坑 3：相似度阈值乱用
  0.7 是经验值！不同模型/不同数据的阈值差异很大
  用真实数据跑分布再定阈值

坑 4：向量和源文本必须一起存
  只存向量不存文本 → 检索到了却拿不到原文 → 白搭
```

## 十一、深度原理：ANN 算法内部机制

### 11.1 HNSW 的完整机制

```
HNSW = 多层图（每层是一个"小世界网络"）

图的构建（插入过程）：
  1. 新向量从顶层开始，贪婪搜索找最近邻
  2. 在适当层插入节点，与该层的 m 个近邻连边
  3. 层次由概率函数决定（越底层节点越多）
     P(层) = exp(-|层|/mL)（mL 控制每层概率）
  顶层：只有几个节点（快速粗定位）
  底层：所有节点（精细搜索）

搜索过程（查询）：
  1. 从顶层入口节点开始
  2. 贪婪搜索：每步走到"比当前更近"的邻居
  3. 没有更近的邻居 → 下到下一层继续
  4. 底层搜完 → 返回候选列表（efSearch 个）
  5. 对候选列表排序，返回 Top-K

三个核心参数：
  M：每节点最大连接数（越大越准越慢，默认 16）
  efConstruction：建图时搜索宽度（越大图质量越高，64）
  efSearch：查询时搜索宽度（越大越准越慢，动态调）

时间复杂度的直觉：
  搜索 = 顶层几步 + 中层几步 + 底层局部搜索
  每层常数步 → 总步数 ≈ 层数 × 常数 ≈ O(log n)
  这就是比暴力 O(n) 快的原因
```

### 11.2 IVF 的完整机制

```
IVF = 聚类 + 倒排

建库（训练阶段）：
  1. 用 K-Means 把全部向量聚成 nlist 个簇
  2. 每个簇一个"倒排列表"（存簇内向量）

查询：
  1. 算查询向量到每个簇中心的距离
  2. 选最近的 nprobe 个簇
  3. 只在选中的簇内暴力搜索

参数权衡：
  nlist 大（如 4096）：簇多而小 → 搜索快但可能漏（查询落在簇边界）
  nlist 小（如 256）：簇大而少 → 搜索慢但召回高
  nprobe 大：搜更多簇 → 更准更慢
  （经验：nlist = 4×√N；nprobe = nlist 的 1%-10%）

IVF vs HNSW：
  IVF：建库快、内存小（可用 PQ 压缩）→ 适合超大库（亿级）
  HNSW：查询快、召回高、内存大 → 适合百万级高质量检索
  pgvector 两者都支持（IVFFlat 和 HNSW）
```

### 11.3 PQ 乘积量化的数学

```
核心思想：把高维向量拆成子向量，每段用码本索引压缩

压缩过程：
  1. 把 d 维向量切成 m 段（每段 d/m 维）
  2. 对每一段分别做 K-Means 聚类（每段 k 个中心 = 码本）
  3. 每个向量每段存"最近中心的编号"
     每段编号 log2(k) 比特
  例：d=1024, m=64, k=256：
     原存储：1024×4B = 4KB
     压缩后：64×1B = 64B（1/64！）

查询：非对称距离计算（ADC）
  查询向量不压缩（保留精度）
  每个子段查码本 → 预计算距离表 → 累加
  计算量大幅减少

代价：有损（量化误差）→ 召回率略降
  工业界：IVF + PQ 组合（IVF-PQ）用于亿级向量
```

### 11.4 ANN 检索的评估指标

```
召回率（Recall@K）：
  精确 Top-K（暴力搜索） ∩ 近似 Top-K 的比值
  例：精确的前 10 个，ANN 找到了 8 个 → Recall@10 = 0.8
  目标：0.9-0.99（视业务）

QPS（每秒查询数）：
  吞吐能力，与硬件强相关

延迟（Latency）：P50/P95
  用户感知指标

内存占用：
  索引占多少 RAM（HNSW 约 1-2 倍向量大小）

三者的权衡曲线（参数扫描）：
  调大 efSearch → 召回↑ 延迟↑ 内存不变
  调大 M → 召回↑ 内存↑ 建图慢
  实际做法：按业务需求（延迟预算）选参数，画召回-延迟曲线
```

### 11.5 pgvector 索引调优实战

```sql
-- HNSW 索引创建（推荐）
CREATE INDEX ON embeddings USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- 查询时动态调 ef_search（每次查询可不同！）
SET hnsw.ef_search = 100;  -- 越大越准越慢

-- IVFFlat 索引（数据量>100万时考虑）
CREATE INDEX ON embeddings USING ivfflat (embedding vector_cosine_ops)
  WITH (lists = 100);  -- 需先有足够数据再建！
-- 查询时调 probes
SET ivfflat.probes = 10;

调优流程：
  1. 用你的真实数据建索引
  2. 写脚本：扫描 ef_search ∈ {40, 80, 120, 200}
  3. 记录每组 (Recall@10, P95延迟)
  4. 画曲线，选"召回达标且延迟可接受"的点
  5. 不要相信默认值！参数必须按你的数据标定
```

### 11.6 什么时候必须升级专用向量库

```
pgvector 的边界：
  1. 数据量：千万级以内没问题（百万级很轻松）
  2. QPS：单机几十到几百 QPS（取决于硬件和参数）
  3. 功能：过滤、聚合、事务都靠 SQL（反而是优势）

升级信号（考虑 Milvus/Qdrant）：
  □ 向量超过 1000 万条
  □ 需要分布式/水平扩展
  □ 需要更高的 QPS（>1000）
  □ 需要特殊索引（如过滤后的 ANN、多向量）
  □ 混合检索（向量+全文）在一体化引擎里性能更好

迁移代价：数据导出重导 + 应用层代码替换
  → 预留好"向量访问抽象层"（接口化）
```
