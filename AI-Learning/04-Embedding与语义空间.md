> **核心问题**：计算机怎么表示"意思相近"？

## 一、什么是 Embedding？

**Embedding（嵌入/向量化）** 就是把文本转换为一组数字（向量），使得：

```
"候选人"     → [0.12, -0.34, 0.78, 0.56, 0.21, ...]  ← 1536 维
"求职者"     → [0.11, -0.32, 0.80, 0.55, 0.23, ...]  ← 语义相近，向量相近
"数据库"     → [-0.45, 0.67, -0.12, 0.03, -0.88, ...] ← 语义不同，向量远离
```

**一句话总结**：Embedding 把"语义"编码成"几何位置"。

---

## 二、语义空间（Semantic Space）

想象一个三维空间（实际是 1536 维或更高）：

```
                    候选人类词汇
                    ↑
                    |
      求职者 ●       |
                    |
        候选人 ●    |
                    |
 数据库 ●           |
  (远离，因为语义不同)
```

**核心规律**：
- **语义相近** → 向量距离近（候选人与求职者）
- **语义相反** → 向量距离远
- **词与词之间**：`国王 - 男人 + 女人 ≈ 女王`（经典的词向量运算）

### 为什么"向量距离"能表示语义？

因为 Embedding 模型（如 BERT、BGE、text-embedding 系列）在训练时被要求：
- 出现在相似上下文的文本 → 映射到相近的位置
- 训练数据量足够大时，模型学会了"语义的几何结构"

## 三、Embedding 模型是怎么工作的？

### 3.1 训练目标（核心思想）

Embedding 模型（如 Sentence-BERT）的训练目标是：

```
输入一对文本 (A, B)
- 如果 A 和 B 语义相似（比如"简历"和"个人履历"）→ 让它们向量距离更近
- 如果 A 和 B 语义不相关（比如"简历"和"数据库索引"）→ 让它们向量距离更远
```

数学上用**对比学习（Contrastive Learning）**实现：

```
Loss = -log( 相似对的距离 / (相似对距离 + 不相似对距离) )

训练过程就是不断调整模型参数，让 Loss 越来越小
```

### 3.2 推理过程

```java
// 你调用 Embedding API 的本质：
String text = "候选人张三有5年Java经验";
float[] vector = embeddingModel.embed(text);
// vector = [0.123, -0.456, 0.789, ...] 共 1536 个 float
```

**输入**：文本 → Tokenizer 分词 → Transformer 前向计算 → **输出**：一个向量

### 3.3 为什么有不同维度的 Embedding？

| 维度 | 模型示例 | 特点 |
|------|---------|------|
| 384 | all-MiniLM-L6-v2 | 小、快、轻量 |
| 768 | BGE-small / E5-small | 平衡 |
| 1024 | BGE-large | 较准 |
| 1536 | text-embedding-ada-002 | OpenAI 经典模型 |
| 3072 | text-embedding-3-large | 更准 |

**维度越高** → 表达力越强 → 但存储/计算成本越高 → 检索越慢

## 四、相似度计算：向量距离

有了向量，怎么判断"有多相似"？

### 4.1 余弦相似度（Cosine Similarity）—— 最常用

```java
// 余弦相似度 = cos(夹角) = (A·B) / (|A| × |B|)
// 范围: -1 ~ 1
// 1 = 完全同向（最相似）, 0 = 垂直（无关）, -1 = 完全相反

public double cosineSimilarity(float[] a, float[] b) {
    double dot = 0, normA = 0, normB = 0;
    for (int i = 0; i < a.length; i++) {
        dot += a[i] * b[i];
        normA += a[i] * a[i];
        normB += b[i] * b[i];
    }
    return dot / (Math.sqrt(normA) * Math.sqrt(normB));
}
```

**为什么用余弦而非欧氏距离？**
- 余弦关注**方向**（语义倾向），对长度不敏感
- 欧氏距离关注**距离**，受向量长度（文本长度）影响大

### 4.2 其他距离

| 方法 | 公式 | 适用 |
|------|------|------|
| 余弦相似度 | A·B / (|A||B|) | 语义检索（最常用）|
| 欧氏距离 | sqrt(Σ(Ai-Bi)²) | 空间聚类 |
| 内积 | Σ Ai×Bi | 归一化向量时等价于余弦 |

### 4.3 实际阈值参考

```
余弦相似度 > 0.8   → 高度相关（同一话题的表述）
余弦相似度 0.6-0.8 → 相关（同一领域）
余弦相似度 0.4-0.6 → 弱相关（可能沾边）
余弦相似度 < 0.4   → 基本无关

（阈值因模型而异，需要在实际数据上校准！）
```

## 五、你项目中的 Embedding 实践

### 5.1 人岗匹配是怎么做的？

```
候选人简历 → Embedding → 简历向量 [0.1, 0.3, ...]
职位描述   → Embedding → 职位向量 [0.2, 0.1, ...]
相似度 = cosine(简历向量, 职位向量) = 0.78
```

这就是你项目中**人岗匹配**的底层原理：
- 不再靠关键词匹配（"Java" 出现次数）
- 而是语义匹配（"精通Spring全家桶" 和 "熟悉Spring Boot" 也能匹配上）

### 5.2 RAG 检索是怎么做的？

```
用户提问 → Embedding → 问题向量
向量数据库：把所有文档 chunk 的向量与问题向量算相似度
取 Top-K 最相似的 chunk → 作为 LLM 的上下文
```

### 5.3 常见坑（务必注意）

**坑 1：不同模型产出的向量不能混用**
```
用 BGE 生成的简历向量，不能用 text-embedding 模型算相似度！
不同模型的向量空间完全不同。
```

**坑 2：文本归一化预处理**
```
// 建议：同一批数据使用相同的预处理（去空格、统一大小写）
// 否则同样内容的向量会偏差
```

**坑 3：相似度阈值需要调**
```
不要直接用网上别人说的 0.7 阈值！
用你自己的数据跑一批测试样本，画出相似度分布，再定阈值。
```

## 六、Embedding vs LLM 生成——两者关系

```
Embedding 模型（小而快）：
  输入: 文本 → 输出: 向量
  用途: 检索、匹配、分类
  成本: 极低（一次调用几分钱，本地 Ollama 免费）

LLM（大而全）：
  输入: 文本 → 输出: 新文本
  用途: 理解、生成、推理
  成本: 较高

RAG 的经典组合：
  用 Embedding 找到"相关文档"（便宜）
  用 LLM 基于文档"生成回答"（贵但值得）
```

## 七、Embedding 的其他应用

| 应用 | 原理 |
|------|------|
| 语义搜索 | 查询向量 × 文档向量 → 相似度排序 |
| 文本聚类 | 相似向量自动归为一类（简历分类）|
| 推荐系统 | 用户偏好向量 × 物品向量 → 推荐 |
| 去重/查重 | 两文档相似度 > 0.95 → 判定重复 |
| 异常检测 | 与正常文本距离太远的向量 → 异常 |
| 分类 | 文本向量 + 分类器（LR/SVM）|

## 八、本课小结

```
核心要点：
1. Embedding 把文本变成向量，语义相近 → 向量相近
2. 训练方式：对比学习（相似对拉近，不相似对推远）
3. 相似度计算：余弦相似度最常用（关注方向，对长度不敏感）
4. 维度越高越准越贵，按场景选模型
5. 不同模型的向量不能混用！阈值需要用自己的数据校准
6. Embedding 便宜适合检索，LLM 贵适合生成——RAG 结合两者
```

## 十一、深度原理：Embedding 是怎么学出来的

### 11.1 Word2Vec：Embedding 的鼻祖

```
2013 年 Word2Vec 证明了"向量能承载语义"，核心思想：

"一个词的意思由它的上下文决定"（分布假说）

两种架构：

CBOW（Continuous Bag-of-Words）：
  用上下文词预测中心词
  "我 [___] Java 开发" → 预测空格填"做/是"
  （周围词 → 预测中间词）

Skip-gram：
  用中心词预测上下文词
  "做" → 预测周围可能出现的词（我/Java/开发）
  （中心词 → 预测周围词）

训练后：词向量表里每个词一行数字
  语义相近的词向量相近（因为它们的上下文相近）

负采样（Negative Sampling）：
  真实上下文中"做"和"Java"相邻 → 拉近向量
  随机采样"不相关的词"（如"数据库"）→ 推远向量
  避免计算整个词汇表的 softmax（太贵）
```

**与 LLM Embedding 的关系**：
```
Word2Vec：静态词向量（一个词一个向量，不管上下文）
  "苹果"（水果）和"苹果"（公司）向量一样 ← 致命缺陷

现代 Embedding（BERT/BGE）：上下文感知
  同一个词在不同句子中向量不同
  例："苹果很好吃" 和 "苹果发布新手机" 中"苹果"向量不同
  这就是"上下文 Embedding"胜过"静态向量"的原因
```

### 11.2 从词向量到句子向量（池化策略）

```
BERT 类模型输出每个 token 的向量，怎么得到整个句子的向量？

方案 1：CLS token（BERT 的传统做法）
  句子开头加 [CLS] 特殊 token
  用它最后一层的向量代表整句
  （训练时 [CLS] 被训练为"汇总全句"）

方案 2：Mean Pooling（均值池化）⭐ 句子 Embedding 主流
  所有 token 向量求平均
  简单、稳定、效果好（BGE/E5 都用）

方案 3：Max Pooling（最大池化）
  逐维度取最大值
  强调"最突出特征"，但可能丢失整体信息

方案 4：加权池化（高级）
  按 token 重要性加权平均（如 IDF 权重）

为什么均值池化够用？
  句子语义是"所有词义的融合"
  平均 = 每个词贡献一份，符合直觉
  （对长文本，切块后逐块 embedding 再平均也可行）
```

### 11.3 对比学习的数学：InfoNCE 损失

```
现代 Embedding 模型（BGE、E5、text-embedding-3）的训练目标：

对每个样本构造：
  正样本对：语义相同的两个文本（如：简历片段 ↔ 岗位要求）
  负样本对：语义无关的两个文本（随机配对）

InfoNCE 损失：

  L = -log [ exp(sim(q, p) / τ) / Σ exp(sim(q, pᵢ) / τ) ]

  分子：查询与正样本的相似度（希望大）
  分母：查询与所有样本（1 正 + N 负）相似度之和（希望正样本突出）
  τ（温度）：缩放相似度，控制"对难负样本的敏感度"

直觉：
  模型在学"把正样本对拉近，把负样本对推远"
  负样本越多越难 → 模型学到的语义边界越精细

难负样本（Hard Negative）：
  与查询"表面相似但语义不同"的样本
  例：查询"Java开发经验" → 负样本选"Java学习教程"而非"会计经验"
  逼模型学到真正的语义区别
```

### 11.4 余弦相似度与欧氏距离的数学关系

```
对单位向量（归一化后）：

  ||a - b||² = ||a||² + ||b||² - 2·a·b
             = 1 + 1 - 2·cos(a, b)
             = 2 - 2·cos(a, b)

结论：归一化后，欧氏距离与余弦相似度是"一一对应"的
  欧氏距离小 ⇔ 余弦相似度大

那为什么实际中推荐余弦？
  1. 未归一化时两者不等价（余弦忽略模长）
     例：a=(1,1,1)，b=(2,2,2) 方向相同
       余弦 = 1（完全相似）；欧氏距离 = √3（看着很远）
     文本长度差异会造成模长差异，余弦更公平
  2. 余弦对"方向"敏感，而文本语义主要是"方向"

实践建议：
  入库前对向量做 L2 归一化
  归一化后检索可以用内积（更快）
  你的 pgvector 若用 cosine 运算符，内部会处理
```

### 11.5 维度选择的权衡（数学视角）

```
高维空间的反直觉现象："维度灾难"
  维度过高时，任意两个随机向量都几乎正交（距离趋同）
  → 相似度区分度下降，阈值难定

经验规律：
  维度越高：表达力越强，但"可区分性"未必线性提升
  常见取值：384（小）/ 768（中）/ 1024（大）/ 1536-3072（超大）

选择依据：
  1. 数据量：百万级以下 768-1024 足够
  2. 语言：多语言/中文 → BGE-M3(1024) 表现好
  3. 成本：维度越高，存储（每行多 4 字节/维）和计算越贵
  4. 一致性：同一知识库永远用同一模型（维度不可混）

存储估算：
  100 万条 × 1024 维 × 4 字节 ≈ 4 GB（仅向量列）
  加上 HNSW 索引 ≈ 再翻 1-2 倍
```

### 11.6 企业选型：主流 Embedding 模型对比

```
本地部署（数据不出域）：
  BGE-M3：1024 维，中文强，支持 8K 长文本，Rerank 同族 ⭐
  bge-small-zh：512 维，轻量快
  nomic-embed-text：768 维，英文好

云端：
  text-embedding-3-large：3072 维，最强但最贵
  text-embedding-3-small：1536 维，性价比
  Qwen 系列也有开源 embedding（同 BGE 风格）

你项目的现状：Ollama + 本地模型
  → BGE-M3 是目前中文 RAG 的最优解之一
  → 注意：换模型 = 全量重建向量库（维度可能不同）
```
