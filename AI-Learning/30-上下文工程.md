# 第 30 课：上下文工程

> **核心问题**：Agent 如何在持续交互中保持"情境理解"？上下文工程解决什么？
> **预计时间**：2 天
> **前置知识**：第 09 课（AI Agent）、第 29 课（Agent 框架）

---

## 一、什么是上下文工程？

```
定义：管理 Agent 在持续交互中的"情境理解"

类比（Java 开发视角）：
  上下文工程 = HttpSession 管理 + 缓存策略 + 状态机
  - Session 存什么、不存什么 → 上下文选择
  - Session 过期策略         → 上下文压缩
  - 分布式 Session 共享      → 上下文检索

为什么重要：
  LLM 的上下文窗口有限（4K-128K token）
  Agent 长任务中信息越来越多
  → 必须管理"什么该记住、什么该忘记"
```

---

## 二、为什么上下文工程重要？

### 2.1 有效上下文解剖

```
Agent 需要的上下文类型：

1. 任务上下文（当前目标、进度）
   "用户要筛选 Java 候选人，已完成 3/10"

2. 环境上下文（工具结果、中间数据）
   "搜索返回 32 人，已分析 5 人"

3. 用户上下文（偏好、历史指令）
   "用户偏好 5 年以上经验的候选人"

4. 领域上下文（业务知识、约束）
   "该岗位要求本科以上、微服务经验"

无效上下文（应丢弃）：
  - 过时的中间结果
  - 重复的工具返回
  - 与当前任务无关的历史
```

### 2.2 上下文检索

```
长任务中，不可能把所有历史都塞给 LLM

解决：按需检索相关上下文
  - 类似 RAG 的思路，但检索的是"对话历史"
  - 向量检索：历史消息 Embedding → 按相关性召回
  - 结构化检索：按时间/类型/实体过滤

类比：
  数据库查询：SELECT * FROM history WHERE topic = '当前任务'
```

### 2.3 长程任务挑战

```
短任务（< 5 轮）：上下文直接拼接，问题不大
中任务（5-20 轮）：需要压缩策略
长任务（> 20 轮）：需要检索 + 压缩 + 摘要

挑战：
  1. Token 爆炸：每轮累积，成本指数增长
  2. 注意力稀释：上下文太长，LLM 忽略关键信息
  3. 状态丢失：压缩过度，丢失重要细节
```

## 三、ContextBuilder 实践

### 3.1 设计动机

```
问题：Agent 每轮调用 LLM 时，消息列表怎么组装？

朴素方案：全量拼接（messages.addAll(history)）
  → 短任务 OK，长任务 Token 爆炸

工程方案：ContextBuilder 动态组装
  - 固定部分：System Prompt + 用户画像
  - 动态部分：按策略选择历史消息
  - 检索部分：从记忆库召回相关上下文
```

### 3.2 核心数据结构

```java
public class ContextBuilder {
    private Message systemPrompt;           // 固定：系统提示
    private List<Message> userProfile;      // 固定：用户画像
    private List<Message> recentHistory;    // 动态：最近 N 轮
    private VectorStore longTermMemory;     // 检索：长期记忆
    private int maxTokens = 8000;           // 预算：上下文上限

    public List<Message> build(String currentGoal) {
        List<Message> context = new ArrayList<>();

        // 1. 固定部分（始终包含）
        context.add(systemPrompt);
        context.addAll(userProfile);

        // 2. 检索部分（按相关性召回）
        List<Message> retrieved = longTermMemory
            .search(currentGoal, topK = 5);
        context.addAll(retrieved);

        // 3. 动态部分（在预算内填充最近历史）
        int remaining = maxTokens - estimateTokens(context);
        List<Message> recent = getRecentWithinBudget(remaining);
        context.addAll(recent);

        return context;
    }
}
```

### 3.3 GSSC 流水线

```
GSSC = Gather → Summarize → Select → Compose

1. Gather（收集）：
   收集所有可能的上下文来源
   - 对话历史、工具结果、用户偏好、知识库

2. Summarize（摘要）：
   对冗长内容做压缩
   - 旧对话 → 摘要
   - 工具结果 → 提取关键信息

3. Select（选择）：
   按相关性/重要性筛选
   - 与当前目标相关的消息优先
   - 最近的消息优先

4. Compose（组装）：
   在 Token 预算内组装最终上下文
   - 固定部分 + 检索部分 + 历史部分
```

## 四、NoteTool：结构化笔记

### 4.1 设计动机

```
问题：Agent 长任务中产生的中间结果怎么保存？

方案：让 Agent 自己"做笔记"
  - 类似人类在复杂任务中记笔记
  - 结构化存储，随时可查
  - 比全量历史更紧凑
```

### 4.2 存储格式

```json
{
  "notes": [
    {
      "id": "note_001",
      "timestamp": "2026-09-10T10:30:00",
      "topic": "Java 岗位要求",
      "content": "5年+ Java, 微服务经验, 本科以上, 薪资 30-50K",
      "tags": ["requirement", "java"]
    },
    {
      "id": "note_002",
      "timestamp": "2026-09-10T10:35:00",
      "topic": "候选人张三分析",
      "content": "8年Java, Spring Cloud 经验, 匹配度 92%",
      "tags": ["candidate", "analysis"]
    }
  ]
}
```

### 4.3 核心操作

```java
// NoteTool：Agent 的"笔记本"
public class NoteTool extends Tool {

    // 写笔记
    public void writeNote(String topic, String content, List<String> tags) {
        Note note = new Note(topic, content, tags, Instant.now());
        notes.add(note);
        vectorStore.add(note);  // 同时入向量库
    }

    // 按主题查笔记
    public List<Note> searchNotes(String query, int topK) {
        return vectorStore.search(query, topK);
    }

    // 按标签过滤
    public List<Note> getByTag(String tag) {
        return notes.stream()
            .filter(n -> n.getTags().contains(tag))
            .toList();
    }
}
```

## 五、TerminalTool：即时文件系统访问

### 5.1 设计动机

```
问题：Agent 需要读写外部文件怎么办？

方案：提供文件系统访问工具
  - 读取配置文件、数据文件
  - 写入中间结果、报告
  - 类似 Java 的 File API，但给 Agent 用
```

### 5.2 核心实现

```java
// TerminalTool：文件系统访问
public class TerminalTool extends Tool {

    // 读文件
    public String readFile(String path) {
        // 安全检查：限制在允许目录内
        if (!isAllowedPath(path)) throw new SecurityException();
        return Files.readString(Path.of(path));
    }

    // 写文件
    public void writeFile(String path, String content) {
        if (!isAllowedPath(path)) throw new SecurityException();
        Files.writeString(Path.of(path), content);
    }

    // 列目录
    public List<String> listDir(String path) {
        return Files.list(Path.of(path))
            .map(Path::getFileName)
            .map(Path::toString)
            .toList();
    }
}
```

## 六、长程 Agent 实战案例

```
场景：批量处理 100 份简历并生成分析报告

上下文管理策略：
  1. 任务开始时：
     - 写入笔记："目标：处理 100 份简历，生成分析报告"
     - 写入笔记："进度：0/100"

  2. 每处理 10 份：
     - 摘要已处理的结果
     - 丢弃详细的中间数据
     - 更新进度笔记

  3. 每轮调用 LLM：
     - 固定：System Prompt + 任务笔记
     - 检索：最近处理的简历摘要
     - 动态：当前 10 份的详细数据

  4. 最终生成报告：
     - 汇总所有摘要笔记
     - 一次 LLM 调用生成最终报告

Token 节省：从 100 份全量 → 10 份摘要 + 进度笔记
```

## 七、与 Java Session 管理的类比

```
上下文工程              Java Session 管理
────────────────────────────────────────
ContextBuilder      →   HttpSession 创建
Message 压缩        →   Session 属性序列化
VectorStore 检索    →   分布式 Session 存储（Redis）
Token 预算          →   Session 大小限制
NoteTool            →   Flash Attribute（临时存储）
GSSC 流水线         →   Session 生命周期管理

你的 HR 项目：
  Redis 存储 Agent 状态 → 正是上下文持久化
  WAIT_APPROVAL 状态    →   上下文暂停/恢复
  审计日志              →   上下文归档
```

## 八、本课小结

```
核心要点：
1. 上下文工程 = 管理 Agent 的"情境理解"
2. 核心挑战：Token 有限 vs 信息无限
3. ContextBuilder：动态组装上下文（固定 + 检索 + 历史）
4. GSSC 流水线：收集 → 摘要 → 选择 → 组装
5. NoteTool：Agent 自己"做笔记"，结构化存储中间结果
6. 与 Java Session 管理思路一致
```
