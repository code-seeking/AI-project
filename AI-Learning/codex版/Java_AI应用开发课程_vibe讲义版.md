# Java AI 应用开发课程 - Vibe 讲义版

生成日期：2026-08-09

## 第 1 章：AI 应用开发认知

团队第一次做 AI 功能时，最容易冲进模型选型、Prompt 调参、页面 Demo。跑通以后才发现真正难的是：谁给事实、谁管权限、谁确认结果、错了谁兜底。AI 应用不是一个模型接口，而是一条业务链路。

核心判断：把“会调用模型”改成“能稳定交付一个业务结果”。模型只是一段能力，工程系统才负责确定性。

- LLM 与传统后端的差异：LLM 是概率生成系统，传统后端是确定逻辑系统。企业 AI 的核心工作，是在不确定能力外面包一层确定工程边界。
- AI 应用六层架构：企业 AI 至少包含模型层、上下文层、知识层、工具层、编排层和治理层。缺任何一层，Demo 上线后都会暴露问题。
- Token 与上下文窗口：模型看到的是 token 序列，不是无限记忆。上下文窗口决定模型一次能参考多少信息，也直接影响成本和稳定性。
- 模型能力边界：模型擅长语言理解、生成和归纳，但不天然具备企业实时事实、权限判断和业务执行能力。
- 幻觉的工程本质：幻觉不是简单 bug，而是资料不足、约束不足或目标不清时，模型仍倾向生成合理文本。工程上要用 RAG、工具、拒答和评估约束。
- AI 应用价值判断：不是所有功能都值得 AI 化。适合 AI 的任务通常语言密集、规则复杂、信息分散、人工成本高。
- Java 开发者的优势：Java 开发者擅长系统边界、事务、权限、稳定性和工程化，这正是企业 AI 落地最缺的能力。
- 从聊天到工作流：聊天只是入口，真正的企业价值来自把回答变成流程节点、数据更新、审批建议和可追踪结论。
- 人机协作闭环：AI 负责分析、生成和建议，人负责目标、判断、确认和反馈，系统负责记录过程并推动迭代。
- 学习路线总图：学习要按模型调用、Prompt、Embedding、RAG、Tool、Agent、治理逐层推进，不要一开始就追复杂 Agent。

## 第 2 章：模型 API 与流式聊天

最早大家会在 Controller 里直接写模型 SDK。第一个 Demo 很快，第二个模型、第三个业务线、第四个降级策略一来，代码就开始散。模型 API 工程化，就是把外部不稳定能力包成内部稳定能力。

核心判断：先有 AI Gateway，再有具体模型调用。业务层只关心任务类型、成本等级、质量等级和返回契约。

- Chat Completion 调用链路：一次模型调用包含 system/user 消息、参数、上下文、模型选择、响应解析和错误处理，不只是一个 HTTP 请求。
- System Prompt 与 User Prompt：System Prompt 定义角色和边界，User Prompt 承载具体任务。两者混用会让提示词不可治理。
- 模型参数 temperature/top_p：参数决定输出稳定性和发散度。事实问答偏低温度，创意生成可提高。
- SSE 流式输出：流式输出优化用户感知等待，但带来断线、取消、异常补偿、审计和前端状态管理复杂度。
- 模型路由策略：不同模型适合不同任务。企业要按质量、成本、延迟、隐私和可用性做路由。
- 超时、重试与 fallback：模型服务不稳定是常态。系统必须有超时、有限重试、降级模型和友好错误。
- Token 成本核算：成本由输入 token、输出 token、模型价格、重试、上下文长度和缓存命中共同决定。
- Prompt Cache：重复问题或稳定上下文可以缓存，但必须注意权限、时效和个性化差异。
- OpenAI 兼容接口：兼容接口不代表行为完全一致，参数、流式、错误码和工具调用都要测试。
- 模型调用日志：日志是评估、成本、审计和安全的基础，不能只为排错记录。

## 第 3 章：Prompt 与结构化输出

Prompt 写得越长，团队越觉得安全。但真正出问题时，没人知道哪句话导致行为变化、哪个字段该修、哪个版本该回滚。把 Prompt 当接口协议，才有工程治理的可能。

核心判断：Prompt 要拆成角色、任务、上下文、约束、输出格式、失败策略，并像接口一样版本化和评估。

- Prompt 是接口协议：Prompt 的作用是定义模型执行任务的协议，不是写一段求模型听话的作文。
- 角色与任务拆分：角色定义模型身份，任务定义要完成的工作，拆开后才可复用、测试和治理。
- 上下文选择：上下文围绕任务目标选择，不是越多越好。多余上下文会增加成本并引入干扰。
- Few-shot 示例：少量高质量示例能约束输出风格和判断尺度，但示例必须覆盖边界情况。
- 结构化输出：结构化输出让 AI 结果进入业务系统，必须配合 JSON Schema、Java record、校验和异常处理。
- JSON 修复策略：模型偶尔会输出非法 JSON，系统需要提取、修复、重试和降级。
- 输出字段设计：字段越贴近业务决策，AI 越有价值。字段要区分结论、证据、风险、缺失信息和建议动作。
- Prompt Injection：用户可能通过输入诱导模型忽略规则。防护要结合系统提示词、工具权限和输出校验。
- Prompt 版本管理：Prompt 是线上逻辑，要版本化、灰度、回滚和效果对比。
- Prompt 评估集：没有评估集就无法判断提示词是否变好。评估集要覆盖常见、边界和失败样本。

## 第 5 章：Embedding 与向量库

很多团队第一次做向量检索，都会把正文一切、向量一存、TopK 一查，然后觉得 RAG 完成了。真正上线后才发现，搜到的相似片段可能过期、无权限、不权威，甚至根本不能回答问题。

核心判断：Embedding 只负责召回候选，生产质量来自文本构造、元数据、过滤、重排和评估。

- Embedding 本质：Embedding 把文本映射到高维向量空间，让语义相近的文本在距离上更接近。
- 向量维度：维度由 embedding 模型决定，不同模型向量空间不可混用。
- 相似度度量：常见度量有 cosine、dot product、L2，必须和模型训练方式及索引匹配。
- 语义文本构造：向量化前的文本组织决定召回质量，要把业务字段合成模型能理解的语义画像。
- Chunk 策略：chunk 影响召回粒度。太大干扰多，太小语义不足，要按标题、段落和语义边界切。
- Metadata 设计：元数据用于权限、过滤、溯源和版本治理，是生产级向量库关键。
- pgvector：pgvector 适合 Java 企业项目快速落地，能和 PostgreSQL 事务、SQL、权限结合。
- Milvus/Redis Vector：Milvus 偏大规模检索，Redis Vector 偏低延迟和缓存场景。
- TopK 与阈值：TopK 不是越大越好，阈值要通过评估集校准。
- 语义搜索评估：评估要看是否搜到正确答案、是否排序靠前、是否带正确元数据。

## 第 8 章：Tool Calling

Tool Calling 让模型看起来能查库、调接口、读文件，但真正的执行权不能交给模型。模型只提出意图，应用系统必须做参数、权限、风险、审计和人工确认。

核心判断：工具越小、越只读、越单职责，越适合交给模型调用；写操作和高风险动作必须进入人工确认。

- Tool Calling 本质：Tool Calling 本质 负责把外部能力安全暴露给模型，同时保持权限、校验和审计边界。
