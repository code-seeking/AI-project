# 第 13 课：企业级 LLM 应用架构设计

> **核心问题**：生产环境的 AI 系统怎么设计才稳定、可靠、可演进？
> **预计时间**：2 天
> **前置知识**：第 12 课（AI 应用工程化）

---

## 一、从"能跑"到"能生产"的差距

```
Demo 阶段：一个 Controller 直接调 LLM API，能返回结果就 OK
生产阶段：要考虑 10 倍以上的问题：

  ❓ 模型挂了怎么办？（供应商故障）
  ❓ 流量翻 10 倍怎么办？（限流、排队）
  ❓ 密钥泄漏怎么办？（密钥管理）
  ❓ 用户投诉"AI 乱说"怎么办？（日志追溯）
  ❓ 要换更便宜的模型怎么办？（解耦）
  ❓ 测试环境和生产环境模型不一样怎么办？（环境隔离）
```

**企业级架构的核心目标**：可用性、可扩展性、可维护性、成本可控、安全合规。

---

## 二、企业级 AI 分层架构

```
┌─────────────────────────────────────────────────┐
│ 接入层（API / Web / 消息队列）                     │
│  统一鉴权、限流、防刷                              │
├─────────────────────────────────────────────────┤
│ 编排层（业务逻辑 + AI 编排）                       │
│  工作流引擎、Agent、RAG 管线、业务规则             │
├─────────────────────────────────────────────────┤
│ AI 服务层（AI Gateway）                          │
│  多模型路由、故障转移、Prompt 模板、语义缓存、追踪  │
├─────────────────────────────────────────────────┤
│ 模型层（Model Provider）                         │
│  云 API（GPT/Claude/Qwen/DeepSeek）             │
│  私有化（Ollama / vLLM / 开源模型）               │
└─────────────────────────────────────────────────┘
```

### 为什么必须加"AI 服务层"？

```
没有 AI 服务层（直接调）：
  业务代码里散落各种模型调用
  换模型 → 改几十处代码
  供应商挂了 → 全业务挂
  无法统一计费、限流、审计

有 AI 服务层：
  业务只认"统一 AI 接口"
  换模型 = 改一处配置
  供应商挂了 = 自动切换备用
  所有调用统一可观测、可计费
```

## 三、高可用设计（可靠性）

### 3.1 多模型冗余（Multi-Provider）

```
主模型：DeepSeek（便宜，日常任务）
备模型：GPT-4o / Qwen-Max（主模型故障时切换）

切换策略：
  1. 故障切换：主模型连续 N 次失败 → 切备用（熔断）
  2. 降级切换：主模型延迟超过阈值 → 切备用
  3. 按任务路由：简单任务走便宜模型，复杂任务走强模型

实现要点：
  失败计数 + 熔断窗口（如 5 次失败熔断 60 秒）
  切换后记录日志：什么时候、为什么切换
  恢复探测：定期探活，恢复后切回主模型
```

### 3.2 重试与退避（Retry with Backoff）

```java
// 重试策略（企业级）
// 1. 可重试错误：超时、429 限流、5xx
// 2. 不可重试错误：400 参数错、401 密钥错、内容审查拒绝
// 3. 退避：指数退避 + 抖动（避免惊群）

int retries = 3;
long delay = 1000;
for (int i = 0; i < retries; i++) {
    try {
        return callLlm(prompt);
    } catch (RateLimitException | TimeoutException e) {
        if (i == retries - 1) throw e;
        Thread.sleep(delay + new Random().nextInt(500)); // 抖动
        delay *= 2; // 指数退避
    }
}
```

### 3.3 降级（Graceful Degradation）

```
降级阶梯（从好到差）：
  1. 主模型 → 备用模型（功能不变）
  2. 强模型 → 弱模型（质量略降）
  3. LLM 生成 → 规则/模板生成（功能简化）
  4. 返回缓存结果（可能是旧数据）
  5. 友好错误提示（明确告知 AI 暂时不可用）

关键原则：业务主流程永远不能被 AI 故障拖死
你项目的实践：AI 服务故障时，人工流程仍可正常使用
```

### 3.4 隔离与保护（Bulkhead）

```
防止单个慢请求拖垮整个服务：
  1. 线程池隔离：AI 调用用独立线程池（别和业务线程池共用）
  2. 信号量限流：并发 AI 调用数上限
  3. 超时兜底：AI 调用必须有超时（如 30s），不能无限等
  4. 队列削峰：大量请求时排队处理，而不是全部打爆模型
```

## 四、环境与配置管理

### 4.1 多环境隔离

```
环境         模型配置             用途
dev         Ollama（本地免费）     开发调试
test        Ollama / 便宜模型     测试验证
staging     生产同款模型（小流量）  预发布验证
prod        正式模型 + 备用模型    线上

每套环境独立：
  模型 API Key、模型名、参数（temperature）
  知识库（独立向量库）
  配置中心统一管理（不硬编码！）
```

### 4.2 配置管理最佳实践

```
1. 配置中心/配置文件（application-{env}.yml）
2. 密钥用环境变量/密钥管理服务（绝不提交到代码库！）
3. 模型参数（temperature、top_p）也配置化，便于调优
4. Prompt 模板放数据库/配置中心，支持热更新

你项目的实践：.env.test / .env.staging / .env.local 多环境配置
```

## 五、灰度发布与版本管理

### 5.1 AI 功能灰度发布

```
AI 功能改动的风险高（Prompt 改一行，效果可能大变）

灰度策略：
  1. 按用户灰度：10% 用户用新版，90% 用旧版
  2. 按请求灰度：新 Prompt 处理 10% 流量
  3. 观察指标：错误率、延迟、用户反馈、成本
  4. 稳定后全量：有问题的及时回滚（保留旧版本配置）

Prompt 版本管理：
  每次修改记录：版本号、修改人、修改时间、修改原因
  线上随时可回滚到任意历史版本
```

### 5.2 模型版本切换

```
模型提供商会更新模型版本（如 GPT-4o-2026-05）
切换前：
  1. 用黄金数据集跑一遍新旧版本对比
  2. 确认质量不降级再切换
  3. 切换后监控指标一段时间（灰度观察期）
```

## 六、数据流设计（企业级考量）

### 6.1 异步化

```
同步场景：用户在线问答（必须等结果）→ 同步 + 流式
异步场景：批量简历分析、报告生成 → 消息队列 + 任务系统

你项目的实践：
  批量分析 → 任务队列 + 状态跟踪 + 结果通知
  在线问答 → 同步流式

异步化的好处：
  1. 长任务不阻塞用户
  2. 失败可重试（消息队列保证）
  3. 流量削峰（排队处理）
  4. 进度可追踪（任务状态机）
```

### 6.2 流式输出（Streaming）

```
为什么企业必须支持流式：
  1. 用户体验：首字快（200ms vs 10s）
  2. 超时容忍：长回答不会连接超时
  3. 成本感知：用户可以实时看到生成（可中断）

实现：
  前端：EventSource / WebSocket / fetch stream
  后端：SSE（Server-Sent Events）逐 token 推送
```

### 6.3 幂等与重放

```
用户重复点击"生成" → 可能重复扣费、重复执行

企业级方案：
  1. 请求 ID（requestId）：每次调用生成唯一 ID
  2. 幂等表：相同 requestId 直接返回上次结果
  3. 前端防抖 + 后端幂等双重保障
```

## 七、企业架构选型清单

```
设计一个 AI 功能前，问自己：

□ 调用模型：直连 / AI 服务层？
□ 同步 or 异步？是否需要流式？
□ 超时、重试、降级策略分别是什么？
□ 哪些操作需要人工确认？
□ 数据脱敏了吗？日志会记录敏感信息吗？
□ 成本预估多少？有预算上限吗？
□ 出问题怎么排查？（有没有追踪日志）
□ 如何验证效果？（评估方案）
□ 上线后如何灰度？如何回滚？
```

## 九、本课小结

```
核心要点：
1. 企业级 = 接入层/编排层/AI服务层/模型层 四层架构
2. AI 服务层是关键：统一入口、路由、故障转移、可观测
3. 高可用三件套：多模型冗余、指数退避重试、分级降级
4. 隔离保护：独立线程池、信号量、超时兜底
5. 多环境隔离 + 配置中心 + 密钥管理
6. 灰度发布 + Prompt 版本管理 + 可回滚
7. 异步化 + 流式输出 + 幂等设计
```
