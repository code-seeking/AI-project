# 第 21 课：AI 可观测性与运维

> **核心问题**：AI 系统出问题怎么第一时间发现、定位、修复？
> **预计时间**：2 天
> **前置知识**：第 13 课（企业架构）、第 14 课（成本经济）

---

## 一、为什么 AI 系统更难运维？

```
传统系统的故障：代码 bug、数据库慢、内存泄漏 → 报错清晰

AI 系统的故障：
  ✗ 不报错！模型"优雅地"输出错误答案（幻觉）
  ✗ 没有异常栈，只有"回答不对"
  ✗ 同样的输入，今天对明天错（模型更新/参数波动）
  ✗ 性能劣化是渐进的（上下文变长 → 越来越慢）
  ✗ 成本失控是静默的（token 慢慢涨）

结论：AI 运维 = 传统监控 + LLM 专属观测
```

---

## 二、可观测性三大支柱（LLM 版）

```
日志（Logs）：每次调用的记录（脱敏）
指标（Metrics）：可聚合的数字（错误率、延迟、成本）
追踪（Traces）：一次请求的完整链路（检索→LLM→工具）

三者的关系：
  指标告诉你"出事了"
  日志告诉你"出了什么事"
  追踪告诉你"问题出在哪个环节"
```

---

## 三、LLM 专属指标（必监控）

### 3.1 功能指标

```
调用成功率：成功调用 / 总调用（< 95% 要警惕）
重试率：发生重试的比例（> 10% 说明不稳定）
JSON 解析失败率：输出格式错误的比例（> 2% 要优化 Prompt）
空响应率：返回空/拒绝回答的比例
超时率：超过阈值的调用占比
```

### 3.2 性能指标

```
TTFT（Time To First Token）：首 token 延迟 ⭐ 用户体验关键
  目标：< 2s（本地）/ < 5s（云端）
  优化：流式输出、模型选择、网络优化

总耗时：请求发出 → 完整返回
  分环节：检索耗时、LLM 耗时、工具耗时

Token 吞吐：每秒生成 token 数（感受生成速度）
```

### 3.3 成本指标

```
每日 token 用量（输入/输出分开）
每日成本（按功能/模型/用户维度）
单次平均成本（变化趋势）
成本异常检测（环比突增 50% → 告警）
```

### 3.4 质量指标

```
用户反馈率：赞/踩比例（越低越好）
无结果率：RAG 检索不到内容的比例
修正率：用户/AI 结果被人工修改的比例（越高说明 AI 越差）
采纳率：AI 建议被业务采纳的比例（最终价值指标！）
```

## 四、链路追踪实现

### 4.1 追踪数据结构

```json
{
  "trace_id": "t-20260807-001",
  "request_id": "r-20260807-001",
  "user_id": "u-1001",
  "feature": "resume_analysis",
  "start_time": "...",
  "spans": [
    {"name": "prompt_build", "duration_ms": 2, "status": "ok"},
    {"name": "embedding", "duration_ms": 15, "status": "ok"},
    {"name": "vector_search", "duration_ms": 8, "status": "ok"},
    {"name": "llm_call", "duration_ms": 2400, "status": "ok",
     "model": "deepseek-chat", "prompt_tokens": 1800, "completion_tokens": 420},
    {"name": "output_validate", "duration_ms": 3, "status": "ok"}
  ],
  "total_ms": 2430,
  "result": "success"
}
```

### 4.2 实现方式

```java
// Spring AOP 统一拦截 AI 调用（你项目可复用的模式）
@Aspect
@Component
public class LlmAuditAspect {

    @Around("@annotation(LlmTrace)")
    public Object trace(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.currentTimeMillis();
        TraceContext ctx = TraceContext.start(pjp.getSignature().getName());

        try {
            Object result = pjp.proceed();
            ctx.success(System.currentTimeMillis() - start);
            return result;
        } catch (Exception e) {
            ctx.fail(e.getMessage());
            throw e;
        } finally {
            auditRepository.save(ctx.toRecord()); // 审计入库
        }
    }
}
```

### 4.3 采样策略

```
全量记录 vs 采样：
  全量：记录所有请求（日志量大、成本高）
  采样：记录 100% 失败 + 10% 成功（平衡）

最佳实践：
  失败请求：100% 记录（排查必须）
  成功请求：10-30% 采样（趋势分析够用）
  慢请求：100% 记录（> P95 的）
```

## 五、告警设计

### 5.1 告警规则（示例）

```
P0（立即响应，页面功能挂）：
  成功率 < 50%（5 分钟）
  全部模型不可用
  LLM 服务大面积超时

P1（关注，体验受损）：
  成功率 < 90%（10 分钟）
  P95 延迟 > 10s
  成本日环比 > 100%

P2（趋势，提前干预）：
  成功率持续缓慢下降（24h）
  单功能成本周环比 > 30%
  无结果率 > 10%
```

### 5.2 告警渠道

```
P0：电话/短信（必须有人醒着响应）
P1：钉钉/企业微信/邮件（5 分钟内响应）
P2：日报/周报汇总（次日处理）

你项目实践：AI 服务故障邮件通知（可升级为多级告警）
```

## 六、故障排查手册（Runbook）

```
场景 1：AI 回答质量突然变差
  排查：
    1. 是不是模型供应商更新了版本？（查公告）
    2. 是不是 Prompt 被改了？（查版本记录）
    3. 是不是检索质量下降？（查检索指标）
    4. 是不是数据变了？（知识库更新？）
    5. 对比：拿昨天的日志重放，看是否复现

场景 2：调用全部超时
  排查：
    1. 模型供应商状态页（是否故障）
    2. 网络连通性（ping/HTTP 探测）
    3. API Key 是否过期/欠费
    4. 本地模型：GPU 是否被占满（nvidia-smi）
    5. 自动切换备用模型（熔断器是否生效）

场景 3：成本暴涨
  排查：
    1. 哪个功能/哪个用户用量激增？（成本报表）
    2. 是不是有人写脚本刷接口？（防滥用）
    3. 是不是输入长度变长了？（Prompt 改坏？）
    4. 是不是重试风暴？（模型不稳定导致连环重试）
    5. 立即措施：熔断非核心功能 + 限流

场景 4：输出格式大量解析失败
  排查：
    1. 模型版本更新？（输出风格变了）
    2. Prompt 示例是否合法？（Few-shot 教坏）
    3. 输入异常？（超长/特殊字符）
    4. 对策：加解析容错 + 修复 Prompt + 灰度
```

## 七、成本运维（FinOps）

```
AI FinOps 循环：
  预测（预算）→ 监控（实际）→ 分析（偏差）→ 优化（手段）→ 再预测

月度流程：
  1. 月初：设定预算（总 + 分功能）
  2. 每日：成本看板（实际 vs 预算）
  3. 每周：分析异常（哪个功能超了？为什么？）
  4. 每月：优化总结（做了什么、省了多少）
  5. 调整：预算重新分配

关键报表：
  成本分布饼图（按功能/模型）
  成本趋势折线（日/周）
  单位成本指标（单次分析成本、单个候选人成本）
```

## 八、值班与应急

```
值班制度：
  值班人：负责当日监控看板 + 告警响应
  交接班：记录当天事件、遗留问题
  应急手册：常见故障的处理步骤（Runbook）

重大故障流程：
  发现 → 响应（5 分钟内）→ 止血（降级/熔断/回滚）
  → 定位（追踪日志）→ 修复 → 复盘（根因/改进/跟进）

复盘模板：
  发生了什么（时间线）
  影响范围（用户/功能/时长）
  根因（为什么）
  改进措施（怎么防止再发生，谁负责，何时完成）
```

## 十、本课小结

```
核心要点：
1. AI 故障"不报错"→ 需要专属观测：日志+指标+追踪
2. 关键指标：成功率、TTFT、JSON 解析失败率、成本、采纳率
3. 追踪：一次请求的完整链路（检索→LLM→工具），AOP 实现
4. 采样策略：失败 100% + 成功 10-30%
5. 告警分级：P0 页面挂 / P1 体验损 / P2 趋势预警
6. 故障手册：质量变差/超时/成本暴涨/格式失败 四大场景
7. AI FinOps：预算→监控→分析→优化循环
```

## 十一、思考题

1. **你们系统现在能回答"这个月 AI 花了多少钱"吗？不能的话需要什么数据？**
